## 二、CLAUDE.md 编写指南

### 2.1 标准模板

```markdown
# {项目名称}

## 项目概述

简要描述项目是什么、做什么的、核心技术栈。

## 开发环境

```bash
# 安装依赖
npm install

# 运行开发服务器
npm run dev

# 运行测试
npm test

# 运行 lint
npm run lint
```

## 项目结构

```
src/
├── components/    # React 组件
├── hooks/        # 自定义 Hooks
├── utils/        # 工具函数
└── pages/        # 页面组件
```

## 编码规范

- 使用 TypeScript strict 模式
- 组件文件不超过 300 行
- 工具函数必须有单元测试
- 禁止使用 any 类型

## Git 工作流

- 分支命名：`feature/{ticket-id}-描述` / `fix/{ticket-id}-描述`
- Commit 格式：`type: 描述`（feat/fix/docs/test/chore）
- PR 要求：至少 1 人 review，通过 CI

## 测试要求

- 单元测试覆盖率 >= 80%
- 关键流程必须有集成测试
- 提交前必须运行 `npm test`

## 安全规范

- 禁止硬编码密钥，使用环境变量
- 所有用户输入必须验证
- 敏感操作必须记录日志
```

# {项目名称}

## 项目概述

[项目简介]

- 前端：React 18 + TypeScript

## 项目结构

```

│   ├── api/              # API 路由和控制器

│   ├── services/         # 业务逻辑
│   ├── middleware/       # 中间件
│   ├── utils/            # 工具函数
│   └── types/            # TypeScript 类型定义
├── tests/
│   ├── unit/             # 单元测试
│   ├── integration/       # 集成测试
│   └── e2e/              # E2E 测试
├── scripts/              # 构建脚本
└── docs/                 # 项目文档
```

## 架构原则

### 1. 分层架构

```
请求 → 路由 → 中间件 → 控制器 → 服务层 → 数据访问层
                      ↓
              （错误处理、日志）
```

### 2. 依赖方向

```
控制器 → 服务层 → 数据访问层
   ↓           ↓
  工具函数   数据库/外部 API
```

### 3. 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 目录 | kebab-case | `user-service/` |
| 文件 | kebab-case | `user-controller.ts` |
| 类名 | PascalCase | `UserController` |
| 函数 | camelCase | `getUserById` |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 类型 | PascalCase | `UserProfile` |

## 代码审查清单

提交 PR 前检查：

- [ ] 代码符合编码规范
- [ ] 有对应的单元测试
- [ ] 测试覆盖率 >= 80%
- [ ] 无硬编码密钥
- [ ] 文档已更新（如需要）
- [ ] `npm run lint` 通过
- [ ] `npm test` 通过

## 常见问题

### Q: 如何添加新的 API 路由？
A: 在 `src/api/` 下创建 `xxx-routes.ts`，在 `src/api/index.ts` 注册。

### Q: 如何添加新的环境变量？
A: 在 `.env.example` 添加注释说明，在 `.env` 填写实际值（不要提交）。

### Q: 测试文件放哪里？
A: 与被测试文件同目录，命名 `xxx.test.ts`。

## 四、分层规则体系

### 4.1 common 规则

#### rules/common/coding-style.md

```markdown
# Coding Style — Common Rules

## 通用原则

### 1. 可读性优先

- 变量/函数名描述性要强
- 避免缩写（除非是公认缩写）
- 一目了然的代码 > 注释解释的代码

### 2. 函数设计

- 单一职责：每个函数只做一件事
- 参数数量 <= 3（超出使用对象）
- 避免深层嵌套（最多 3 层）

### 3. 错误处理

```typescript
// ✅ 正确：错误被视为一等公民
async function fetchUser(id: string) {
  try {
    const user = await db.users.findById(id);
    if (!user) {
      throw new NotFoundError(`User ${id} not found`);
    }
    return user;
  } catch (error) {
    logger.error('Failed to fetch user', { id, error });
    throw error;
  }
}

// ❌ 错误：吞掉错误
async function fetchUser(id: string) {
  try {
    return await db.users.findById(id);
  } catch {
    return null; // 错误去哪了？
  }
}
```

### 4. 注释规范

- WHY > WHAT：解释为什么，而非做什么
- 复杂逻辑需要注释
- 公共 API 需要 JSDoc

```typescript
// ✅ 正确
// 使用二分查找因为数据量超过 10000 条
// 线性查找会超过性能预算
const index = binarySearch(sortedArray, target);

// ❌ 错误
// 循环查找元素
for (let i = 0; i < arr.length; i++) {
  if (arr[i] === target) return i;
}
```

## 文件组织

- 按功能/领域组织，而非按类型
- 目录深度 <= 3 层
- 单文件行数 <= 500（理想 < 300）
```

## 单元测试

### 原则

- 一个测试函数只测一件事
- Arrange-Act-Assert 模式
- 测试名描述预期行为

### 示例

```typescript
describe('calculateDiscount', () => {
  it('returns 10% discount for orders over $100', () => {
    // Arrange
    const orderAmount = 150;
    const discountTier = 'standard';

    // Act
    const result = calculateDiscount(orderAmount, discountTier);

    // Assert
    expect(result).toBe(15);
  });

  it('returns 0 for orders under $100', () => {
    expect(calculateDiscount(50, 'standard')).toBe(0);
  });
});
```

## 集成测试

### 原则

- 测试组件间的交互
- 使用真实数据库（测试环境）
- 每个 API 端点至少一个测试

## E2E 测试

### 原则

- 只测关键用户路径
- 使用独立测试环境
- 测试完成后清理数据

## 覆盖率要求

- 整体覆盖率 >= 80%
- 新代码覆盖率 >= 90%
- 关键路径覆盖率 100%

## 测试维护

- 测试失败立即修复
- 删除无用的测试
- 保持测试快速（< 5min）
```

## 六、CI/CD 集成

### 6.1 规则检查（可选）

```yaml
# .github/workflows/rules-check.yml
name: Rules Validation

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Validate CLAUDE.md
        run: |
          if [ ! -f CLAUDE.md ]; then
            echo "Error: CLAUDE.md not found"
            exit 1
          fi
      
      - name: Validate rules structure
        run: |
          # 检查规则文件是否存在
          for rule in coding-style git-workflow testing security; do
            if [ ! -f ".claude/rules/common/${rule}.md" ]; then
              echo "Warning: .claude/rules/common/${rule}.md not found"
            fi
          done
```

### 6.2 自动化规则安装

```bash
#!/bin/bash
# scripts/install-team-rules.sh

set -e

RULES_DIR=".claude/rules"
TEMPLATE_URL="https://github.com/org/team-rules-template"

echo "Installing team rules..."

# 创建目录
mkdir -p "$RULES_DIR/common"

# 复制模板规则
cp -r "$TEMPLATE_URL/rules/common/"* "$RULES_DIR/common/"

# 复制语言特定规则（如果有）
if [ -d "$TEMPLATE_URL/rules/$PROJECT_LANG" ]; then
  mkdir -p "$RULES_DIR/$PROJECT_LANG"
  cp -r "$TEMPLATE_URL/rules/$PROJECT_LANG/"* "$RULES_DIR/$PROJECT_LANG/"
fi

echo "Rules installed successfully!"
echo "Please review and customize rules for your project."
```

## 八、常见问题

### Q1: CLAUDE.md 和 AGENTS.md 都存在会冲突吗？

不会。两者可以共存，AI 工具会同时读取：
- CLAUDE.md → Claude Code 专用
- AGENTS.md → 通用代理指令

### Q2: 规则太多会影响 AI 性能吗？

会。建议：
- CLAUDE.md 保持简洁（< 5 KB）
- 详细规则放在 rules/
- 使用分层加载

### Q3: 如何处理规则冲突？

优先级顺序：
1. 用户指令（最高）
2. 项目规则（rules/）
3. 通用规则（common/）

### Q4: Monorepo 应该如何组织规则？

```
root/
├── CLAUDE.md              # 整体项目上下文
├── AGENTS.md              # 通用指令
└── packages/
    ├── app/
    │   ├── CLAUDE.md      # app 特定
    │   └── .claude/rules/ # app 规则
    └── shared/
        ├── CLAUDE.md      # shared 特定
        └── .claude/rules/ # shared 规则
```

### Q5: 如何确保团队成员遵守规则？

1. **教育**：规则文档清晰说明原因
2. **工具**：CI 自动检查
3. **文化**：Code Review 中强调
4. **激励**：规则遵守好的团队成员表扬
