# CLAUDE.md — [项目名称] AI 编程行为准则

> **职责**：定义 AI 编程助手的思维模式、编码风格、开发流程、输出格式
> **适用**：Claude Code（可与 @AGENTS.md 协同使用）
> **定位**：编码思维 + 输出风格 + 开发流程，非项目技术细节

## 一、核心思维总则

### 1.1 任务分析优先
任何任务优先**高层架构分析**，再拆解子步骤，最后落地编码：
1. 理解需求和约束边界
2. 分析对现有架构的影响
3. 确定改动范围和风险
4. 拆解实施步骤
5. 逐步执行和验证

> ⚠️ **禁止**：不分析直接写代码，不理解业务逻辑就动手

### 1.2 最小改动原则
- 只修改必要代码，不做无意义格式化
- 不扩散变更范围，不改动无关文件
- 改动前确认是否影响现有功能

### 1.3 可读性 > 性能
- 优先代码可读性、可维护性
- 拒绝过度设计、炫技写法、冗余抽象
- 性能优化需有明确 profiling 数据支撑

### 1.4 兼容性意识
- 所有修改必须兼容旧逻辑
- 不破坏现有流程
- 隐性风险提前识别并告知

### 1.5 输出简洁务实
- 无空话、无模板客套、无多余解释
- 只给关键结论和可执行代码
- 需要确认时直接提问，不臆测

## 二、编码通用规范

### 2.1 基础原则
1. **单一职责**：函数/类/模块只做一件事
2. **命名语义化**：见名知意，禁止拼音、无意义缩写
3. **常量归一**：枚举、配置项统一抽离，禁止魔法值
4. **异常处理**：统一捕获，不裸抛、不吞异常
5. **复用优先**：优先使用项目已有工具类，禁止重复造轮子

### 2.2 风格一致性
- 新增逻辑遵循项目现有：
  - 分层架构和目录结构
  - 代码风格和命名规范
  - 模块边界和依赖关系
- 不另起一套范式，不制造"个性化"代码

### 2.3 注释规范

| 场景 | 要求 |
|------|------|
| 业务复杂逻辑 | **必须加注释**，说明"为什么"而非"做什么" |
| 边界条件处理 | **必须加注释**，说明特殊处理原因 |
| 历史兼容逻辑 | **必须加注释**，说明历史背景 |
| 简单逻辑 | **不堆冗余注释**，代码本身应自解释 |

## 三、代码修改与重构规则

### 3.1 接手现有代码
```
1. 先读懂原有逻辑、边界条件、历史坑点
2. 理解模块的输入输出和依赖关系
3. 再进行任何改动
```

### 3.2 重构边界
- ✅ **可以做**：提纯、解耦、规整结构
- ❌ **禁止做**：私自变更业务逻辑、改变对外接口

### 3.3 Bug 修复
```
1. 先定位根因，不盲目试错
2. 最小范围修复
3. 附带必要注释说明修复原因
```

### 3.4 禁止行为
- ❌ 不随意删除已有注释
- ❌ 不随意修改已有对外接口、常量定义
- ❌ 不对老旧模块做大改造（只做局部修复）

## 四、单元测试与校验规范

### 4.1 必须配套测试的场景
- 核心业务逻辑
- 公共工具方法
- 边界条件处理
- 异常流程处理

### 4.2 测试质量要求
- ✅ 覆盖正常场景
- ✅ 覆盖边界场景（空值、最大值、特殊字符）
- ✅ 覆盖异常场景（网络失败、权限不足）
- ❌ 不写无意义空测试
- ❌ 不写只跑通不校验的假测试

### 4.3 代码变更后必做
```
1. 执行 lint 检查 → npm run lint / ruff check .
2. 执行单元测试 → npm run test / pytest
3. 确认全部通过后再提交
```

## 五、问题排查与调试规范

### 5.1 排查路径（按顺序）
```
日志 → 链路追踪 → 入参出参 → 分支条件 → 依赖底层
```

### 5.2 排查原则
- 先复现，再定位，再修复，再验证
- 不盲目试错改代码
- 不确定时直接提问

### 5.3 结论输出格式
```
根因：[具体原因]
影响范围：[影响的功能/用户]
修复方案：[具体做法]
注意事项：[后续监控/回归测试建议]
```

## 六、输出格式约束

### 6.1 代码输出
- 只贴关键实现片段，不整文件全量刷屏
- 多处改动时分模块逐条说明
- 复杂改动先给方案结论，再给代码实现

### 6.2 验证说明
- 代码变更后必须给出验证方式
- 明确如何测试、如何验证正确性

### 6.3 不确定处理
- ❌ 不编造配置、不臆测业务参数
- ✅ 不确定时直接提问，而非瞎补

## 九、规则迭代机制

### 触发添加规则
- AI 重复犯同一个错误 2 次以上
- Code Review 中经常出现同类反馈

### 触发删除规则
- 该规则对应的技术已不再使用
- 规则从未被触发（说明可能是冗余的）
- 主文件超过 150 行

### 维护原则
- 规则文件是活文档，需要持续迭代
- 从 Bad Case 出发驱动迭代，是最高效的方式
